## 2. Root cause

The task asked to discriminate among four candidates. The evidence resolves this cleanly.

### Ruled out — throttling

Two requests, two seconds apart, same session. Throttling suppresses the request that arrives
*after* the limit is hit. Here the **first** request failed and the **second** succeeded. That is the
opposite of a rate-limit signature.

Supporting detail: no HTTP 429 was recorded, no rate-limit exception text appears, and the failure
returned in ~2 s rather than after any backoff. The collector's own throttle handling (60 s sleep on
429, per the project's established `HARD_429_SLEEP` convention) never engaged.

### Ruled out — transport failure

A transport fault — connection reset, DNS failure, TLS error, timeout — raises an exception, and the
ledger records exception text. This record instead carries `Refused: empty Trends frame`: a
**well-formed response was received and parsed into a DataFrame**, which was then empty. The HTTP
exchange completed successfully. The ticker query one second later on the same connection confirms
the transport path was healthy.

### Ruled out — pytrends defect

pytrends returned an empty frame. That is pytrends **correctly** representing "Google Trends returned
no series for this term". It is not a library bug, and it is not a parsing error: the collector's own
guard then refused the empty frame rather than silently proceeding — which is the designed and
correct behaviour. `pytrends` version is recorded as `unknown` (see section 4), but no version of it
would manufacture data that Google did not return.

### CONFIRMED — query wording

**Root cause: the issuer query string is below Google Trends' minimum search-volume threshold, so
Trends returns an empty series.**

Google Trends suppresses output entirely for queries whose volume falls under a floor. The literal
string `Ross Stores, Inc. stock` — full legal name, comma, `Inc.`, plus a `stock` suffix — is a
phrasing essentially nobody types into Google. `ROST stock` clears the floor comfortably: 105 rows,
104 complete weeks, a well-defined z of −0.075.

This is **deterministic, not stochastic**. The same query on the same day will return empty every
time. It is a property of the string, not of the network, the session, or the moment.

### Where the defect actually sits

The failure was **generated by the frozen query-identity rule itself**, not by an operational fault.
`QUERY_IDENTITY_RULE_FROZEN` (record 6, frozen 2026-08-19T05:21:06Z, before any request) mandates:

> 1. Use the exact issuer display name from the official issuer investor-relations earnings
>    announcement.
> ...
> 5. Preserve source spelling and punctuation in the submitted query.

Applied faithfully — and it *was* applied faithfully — that rule converts a registrant's legal name
into a search query. Legal names are drafted for securities filings, not typed into search boxes.
Clause 5 in particular guarantees that corporate punctuation (`, Inc.`) is preserved into the query,
which is precisely what pushes the string below the volume floor.

So this is a **design defect in a frozen rule**, discovered on its first live application. It is not
an implementation bug, an infrastructure problem, or operator error.

## 3. What the collector did right

Worth recording explicitly, because the failure is being read as a fault and much of the behaviour
was correct:

- The empty frame was **refused, not repaired**. No zero-filling, no interpolation, no substitution.
- `retry_policy: NONE` was **honoured** — `retried: false`. No second same-day request was made.
- The failure was **written to the append-only ledger with full provenance**: request id, both
  timestamps, exact query string, all request parameters, dependency versions.
- The successful leg **did not paper over** the failed one; the frozen aggregation rule invalidates
  the whole leg rather than falling back to one query (`one_query_fallback: false`).
- The successful leg's raw CSV was archived **repository-external** with a SHA-256, per the
  collection-stage prohibition on committing raw provider responses:
  `trends_2026-08-19_ticker_query_attempt1.csv`, sha256 `e108e567…`, 3,253 bytes, in
  `gst-source-quarantine/TRENDS_2026-08-20_ROST/`.
- `values_committed: false`, `values_printed: false` — no observation values leaked into the record.

## 5. Conclusion

| Candidate cause | Verdict | Decisive evidence |
|---|---|---|
| Query wording | **CONFIRMED** | Identical-parameter ticker query succeeded 2 s later; empty frame is Trends' below-threshold response; failure is deterministic for the string |
| pytrends behaviour | Ruled out as a defect | Empty frame is correct reporting of an empty result |
| Throttling | Ruled out | The *later* request succeeded; no 429; no backoff engaged |
| Transport failure | Ruled out | Response received and parsed; same connection healthy 1 s later |

**The root cause is that the frozen query-identity rule generates search strings from legal registrant
names, and such strings can fall below Google Trends' volume floor. `Ross Stores, Inc. stock` did.**

Any corrected method must address query *construction*, not retry logic. Adding retries would not have
helped: the request did not fail transiently, it returned a correct empty answer, and it would do so
again on every attempt. This distinction matters for the prospective cohort's yield and is developed
in `PROSPECTIVE_COHORT_YIELD_MATH_2026-08-20.md`.
